# スマホで登録し、別端末で所有者を確認する

状態: 相談用UIモックを先に実装。実接続アプリ、CLI、コントラクトは未実装。後半の実接続手順を実施済みとは扱わない。

## チームでUIモックを確認する

[スマホ用プレビュー](https://shomei-kun-ui-mock.dptr.workers.dev/) を開く。最初に「QRコードをスキャン」を押すと模擬カメラ画面に進む。実カメラは起動しない。「サンプルを読み取る」で「おじいちゃんコンビニ」の登録情報を確認できる。

1. 上部の「表示を変更」から「未登録」を選ぶ。[未登録の直接リンク](https://shomei-kun-ui-mock.dptr.workers.dev/?scenario=unregistered) でも開ける。
2. 所有者登録へ進み、ニックネームを入力する。ウォレット接続の説明からサンプルウォレットを接続する。
3. 公開情報に同意し、内容確認・承認へ進む。模擬送信、確認中、完了から公開画面を確認する。
4. 「表示を変更」で別ウォレット、別チェーン、承認拒否、失敗、結果不明、情報取得不能などを比べる。
5. 上部の言語ボタンで日英を切り替える。同じタブの再読込では進行状態と入力が残る。

相談する点は、所有者情報の分かりやすさ、登録前の公開説明、QRから登録までの順序、失敗時の次の操作とする。「この状態のURLをコピー」でサンプル状態を共有できる。入力したニックネームは別端末へ共有されない。

このモックではMetaMask、MultiBaas、Amoyを呼ばず、実際の登録・証明は行わない。カード素材のQRは公開サンプルへのURLで、アプリ内カメラ機能とは別である。詳細は [採用計画](UI_MOCK_PLAN.md)、起動・検証方法は [モックのREADME](../prototypes/mobile-ui/README.md) を参照する。

以下は実接続版を実装した後の手順案。

## 実演の前に準備する

1. Amoy向けMultiBaas環境を利用できることを確認し、APIのURLと権限を設定する。チェーンIDが80002であることを確認し、CLI・MetaMaskの接続先もAmoyに揃える。
2. 発行者ウォレットと登録者ウォレットを分ける。登録者はスマホのMetaMaskアプリを用意する。発行者へ渡すのは公開アドレスだけとする。
3. Amoy用Faucetから、発行者と登録者にガス代用のテストPOLを用意する。利用条件は実行時に確認する。[Polygon公式の設定・資金準備手順](https://docs.polygon.technology/tools/dApp-development/common-tools/remix/)
4. コントラクトをAmoyへ配置し、チェーンID、アドレス、ABI、配置ブロック、発行者を記録する。MultiBaasへ契約を紐付け、配置ブロックからイベント同期を有効にする。
5. Cloudflareにデモアプリを公開する。サーバー側にMultiBaasの接続・契約設定と最小権限のAPIキーを設定する。APIキーや署名鍵がブラウザ配信物に含まれないことを確認する。
6. スマホの通常ブラウザからMetaMaskへの接続、ネットワーク追加・切替、ブラウザへの復帰を確認する。実際の端末・OS・ブラウザ・MetaMaskのバージョンを記録する。
7. ウォレット未接続の閲覧用端末を別に用意する。

通常の読取り、未署名取引の作成、レシート・イベントの取得がMultiBaas API経由で動くことを確認する。APIの障害とイベント同期遅延を試し、未登録や成功へ置き換えないことを確認する。Amoy向け環境の確認ができない場合は準備未完了と記録し、別チェーンへ無断で切り替えない。

MultiBaasやCloudflareの環境設定は事前準備である。カードIDと許可ウォレットの発行操作はCLIで行い、発行者用Web画面は用意しない。具体的な導入・配置コマンドは実装後に動作確認して追記する。

## カードを発行する

1. 未使用のカードIDと登録者の許可ウォレットをCLIに指定する。
2. CLIからMultiBaas APIで未署名取引を作る。対象を確認してCLI側で署名し、Amoyへ送る。MultiBaas APIで成功レシートと発行済み状態を確認する。
3. 公開ページにカードが「未登録」と表示されることを確認する。発行時点で所有者が登録済みになっていないことを確認する。
4. 公開ページURLをQRにし、「証明一郎」のカード右下に配置する。印刷物から読み取れることを確認する。

カード画像の作成・利用時に出典と利用許諾を記録する。QRは公開URLのみとし、登録許可用の秘密、ニックネーム、鍵を埋め込まない。

## スマホで所有者を登録する

1. スマホのカメラでカードのQRを読み、通常ブラウザで公開ページを開く。
2. 「証明一郎」、カードID、未登録の表示を確認し、登録へ進む。
3. ニックネームに「おじいちゃんコンビニ」を入力する。
4. 公開される情報と登録後に変更・削除できないことを確認する。
5. MetaMaskへ接続し、許可されたアドレスとPolygon Amoy、チェーンID 80002になっていることを確認する。
6. アプリがMultiBaas APIで作成した未署名取引の対象カードと登録内容を確認し、MetaMaskで署名・送信を承認する。
7. ブラウザへ戻る。承認待ち、送信済み、記録確認中が区別され、確認完了後に成功になることを確認する。
8. 公開ページを再読込し、「現在の登録所有者」、ニックネーム、ウォレットが同じであることを確認する。

承認を拒否した場合は、その旨の表示と入力画面への復帰を確認する。送信後に通信が途切れた場合は、既存の取引を再確認する。確認不能を失敗や未登録と決め付けて再送しない。

## 別端末から公開情報を確認する

1. ウォレット未接続の閲覧用端末で同じQRを読む。
2. 「現在の登録所有者」が「おじいちゃんコンビニ」であることを確認する。
3. 登録ウォレット、カードID、発行者、チェーンID、コントラクトアドレス、登録取引ハッシュを確認する。外部確認の導線からAmoy Polygonscanを開き、同じ取引・コントラクトを指していることを確認する。
4. 日英表示を切り替え、再読込後も選択が保たれることを確認する。ニックネームが翻訳されず、原文のまま表示されることを確認する。

実演では「この記録は許可されたウォレットによる登録を確認するものです。QRのコピーやカード現物の所持は判定しません」と説明する。

## アプリを介さず登録記録を照合する

この節は照合手順の設計である。実際のコントラクトとABIができた後、第三者がそのまま実行できるコマンドを追記し、実行結果を残す。現時点で再現試験済みとは扱わない。メソッドの意味は [Ethereum JSON-RPC API](https://ethereum.org/developers/docs/apis/json-rpc/) を参照し、利用するAmoy RPCで動作を検証する。

第三者へAmoyの公開RPC、チェーンID 80002、コントラクトアドレス、ABI、カードID、配置ブロック、登録取引ハッシュを提供する。MultiBaasを介さない接続を使い、MultiBaasのAPIキーや発行者の鍵を必要としない手順とする。

1. RPCの `eth_chainId` で、提示されたチェーンIDとの一致を確認する。
2. `eth_getCode` で対象アドレスにコントラクトがあることを確認する。
3. ABIに基づく `eth_call` でカードの存在、発行者、登録状態、所有者、ニックネームを読む。画面の値と比較する。
4. `eth_getTransactionByHash` と `eth_getTransactionReceipt` で登録取引を取得する。成功状態、送信者、送信先、ブロック情報を確認する。
5. レシート内の対象コントラクトの登録イベントをABIで読み、カードID・所有者・ニックネームが状態照会と一致することを確認する。
6. 配置以降の `eth_getLogs` でも対象カードの登録イベントを検索し、提示された取引との対応を確認する。RPCに取得範囲の制限があれば範囲を分ける。

未登録カードには登録取引がない。取引取得が失敗した場合は未登録と決めず、接続と対象を再確認する。画面のAmoy Polygonscanへのリンクでも取引の成功状態、送信者、記録先を確認する。エクスプローラーの障害だけで登録状態を変更しない。

- 試験ID、操作、期待結果、実測結果、合否、未実施項目。
- デスクトップ・390px・320pxの画像と表示確認結果。スマホ実機でのウォレット往復結果。

デモをやり直すときは新しいカードIDを発行する。既存カードの登録を初期化しない。
